# 검증 결과 기록

## 0.1.5 배포 검증

압축 안의 `release.json`과 `VERIFICATION.json`에서 배포 식별자, 실행 파일 SHA-256과
검증 결과를 확인합니다. 이 버전은 pnpm 설치 경로별 관계 및 실패 진단, 두 SBOM 형식의
경로별 검증, 내장 Maven POM 속성과 숫자 버전 범위에 대한 관계 수집을 포함합니다.

## 0.1.4 디렉터리 전용 실행과 최종 배포 식별

0.1.4는 기존 `scan --target <디렉터리> --no-context`를 사용하는 `scan-directory.sh`와 실행 안내를 포함합니다. 특정 디렉터리와 하위만 수집하고 호스트 컨텍스트·라이브패치 조회는 실행하지 않습니다. 디렉터리 밖의 구성요소와 밖으로 향하는 심볼릭 링크가 표준 SBOM에 포함되지 않는지, 공백 경로·제한 해제·잘못된 옵션 거부를 별도로 검증합니다.

이번 최종 실행파일의 검증과 한계는 동봉 `VERIFICATION.json` 및 빌드 PC의 `dist/evidence/v0.1.4/final-verification.json`으로 확인합니다. 아래 기록은 과거 이력이며 새 빌드의 검증 근거를 대신하지 않습니다.

## 0.1.3 최종 배포 검증 식별

0.1.3은 `--max-files`와 수집 시간 제한 해제, helper의 수집 옵션 전달 및 제한 원인 기록을 추가하는 배포입니다. 파일 수 기본 상한은 1,000,000개이며 `--max-files 0`은 해제, 시간 기본 상한은 30분이며 `--timeout 0` 또는 `0s`는 해제입니다. Ctrl+C 취소와 기존 수집 경계는 유지합니다.

새 최종 바이너리의 실제 시험 결과는 동봉 `VERIFICATION.json` 및 `dist/evidence/v0.1.3/final-verification.json`의 SHA-256과 연결해 확인합니다. 이 문서의 과거 결과를 새 바이너리의 통과 증거로 사용하지 않습니다. 파일 수 상한 초과·무제한·취소 처리와 `collection.json`의 `limits`/`filesystemFileCount` 및 구조화된 제한 사유는 새 릴리스의 별도 검증 대상입니다.

## 0.1.2 최종 배포 검증 이력

이전 0.1.0/0.1.1 결과는 아래에 이력으로 보존합니다. 0.1.2의 최종 바이너리,
Ubuntu 24.04.1 `6.8.0-47-generic`와 Oracle Linux 8.2 RHCK·UEK의 재실행 결과는
당시 배포에 동봉했던 `VERIFICATION.json` 및 `dist/evidence/v0.1.2/final-verification.json`으로 기록했습니다.
해시가 다른 과거 바이너리의 결과를 새 최종본의 실행 증거로 사용하지 않습니다.

라이브패치의 커널 sysfs 관측과 Ksplice/Canonical 클라이언트 보고서 수입을 구분합니다.
공급자별 진짜 구독 클라이언트 설치·실제 라이브패치 적용 시험은 포함하지 않습니다.
보고서 파싱·helper 시험은 합성 입력이며, 실제 VM 검증은 공급자 패치를 적용하지 않은 커널의
상태 관측·SBOM·컨텍스트·무결성에 대한 검증입니다. 제품은 CVE 취약성/조치완료 판정을 하지 않습니다.

이 파일에는 실제 수행한 구현 검증과 커널 VM 검증을 기록합니다. 검증에 사용한 빌드와 최종 배포 빌드의 재실행 결과는 구분합니다. 실패·미수행은 별도 표시하며 fixture 검증을 실제 운영 서버의 증거로 사용하지 않습니다.

## 검증 경계

- 빌드 호스트는 macOS ARM64이며 배포 대상은 Linux x86_64입니다.
- Docker의 Linux amd64 실행은 에뮬레이션/가상화된 대상 환경입니다. 아래 Oracle RHCK·UEK 시스템 VM 검증 및 실제 x86_64 물리 서버 검증과 구분합니다.
- Oracle Linux 8.2 컨테이너는 사용자 공간과 RPM DB 검증에만 사용합니다.
- 기존 KODA·Tracker 운영 DB 또는 사용자·점검 결과를 이 검증에 사용하지 않습니다.

최종 배포 아티팩트의 해시는 배포 검증 보고서와 `.sha256` 파일에 기록합니다.

## 2026-10-29 Oracle Linux 8.2 실제 커널 VM

Oracle Linux 8.2 사용자 공간에 공식 서명된 GA 커널 RPM 4개를 설치한 시험 파일시스템을 만들고,
QEMU **시스템** TCG로 RHCK와 UEK를 각각 직접 부팅했습니다. Docker가 공유하는 호스트 커널이나
QEMU user-mode의 uname 대체 값을 이 검증에 사용하지 않았습니다.

시간은 ARM64 호스트의 x86_64 TCG 에뮬레이션 측정값이며 물리 서버 성능 예상값이 아닙니다.
종료 `3`은 보호된 shadow 계열 파일, 수집 범위 밖 또는 해석 불가 링크, OpenSSH의 충돌하는
내장 버전 문자열, Syft 경고를 `collection.json`에 보존한 결과입니다. 해당 사유를 제거하거나
전체 수집 성공 `0`으로 바꾸지 않았습니다. 커널·RPM·모듈 구분 검증 통과와 수집의 완전성은 다릅니다.

이 초기 VM 검증에는 기존 **0.1.0 바이너리** SHA-256
`98384927a272573b0ecd348a55e76d3700008c9677eb3dea16bb76ed2590724b`를 사용했습니다.
0.1.1 최종 포장은 문서·시험 도구를 반영한 새로운 소스 식별자와 바이너리로 구분하며,
**최종 바이너리를 다시 부팅·검증한 결과와 해시**를 `dist/evidence/v0.1.1`의 별도 보고서로 남깁니다.
이 문서에 기록된 초기 VM 결과만으로 새 바이너리의 재실행이 끝났다고 주장하지 않습니다.

검증 도구는 `tests/oracle-vm`에 있습니다. 공식 커널 URL·SHA-256·서명키는
`kernels.json`, 입력 provenance·RPM 서명 로그·QEMU 명령·serial 로그·baseline·validation 결과로
연결합니다. 재현 명령은 [검증 안내](verification.ko.md)에 있습니다.

## 명시적 한계와 미검증

- 실제 x86_64 물리 서버에서는 아직 실행 검증하지 않았습니다. 위 VM은 공식 RHCK·UEK 커널과 Oracle Linux 8.2 사용자 공간의 custom initramfs 직접 부팅 시험입니다. 일반 OS 설치 프로그램·GRUB·UEFI/Secure Boot·systemd 전체 부팅·SELinux enforcing·운영 서비스 통합은 확인하지 않았습니다.
- macOS ARM64 Docker의 amd64 ptrace/strace는 레지스터를 잘못 해석하는 현상이 있어 해당 로그를 무통신 증거로 사용하지 않았습니다. 대체 QEMU guest syscall trace는 실제 amd64 실행 파일의 게스트 동작 증거이며 실제 x86_64 커널에서의 추적과 다릅니다.
- Tracker는 두 표준 SBOM 업로드를 검증했습니다. `context.json`·`collection.json`·`inventory.syft.json` 부가 자료의 자동 반입·화면 표시·백포트/CVE 적용 조건 자동 판정은 현재 지원 완료로 주장하지 않습니다.
- 라이브 파일시스템 수집은 스냅샷이 아닙니다. 수집 중 패키지 설치·업데이트·파일 교체가 있으면 시점이 다른 정보가 섞일 수 있으므로, 변경이 적은 시간에 수행하거나 읽기 전용 OS/파일시스템 스냅샷을 대상으로 사용하세요. 수집기가 정합성 있는 원자적 OS 스냅샷을 만든다고 보장하지 않습니다.
- 패키지 버전·설정 선언·모듈 미관측만으로 CVE 영향 여부나 안전성을 판정하지 않습니다. 상용 제품의 알려지지 않은 patch inventory 형식과 식별정보 없는 바이너리는 unknown/미검증 범위로 남습니다.
