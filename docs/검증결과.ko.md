# 검증 결과 기록

## 2026-11-21 Daybreak 12건 조치 검증

Daybreak가 KODA-SBOM-Maker의 `cc86c1b`에서 보고한 12건을 조치했습니다.
아래 번호는 Daybreak 보고서 순서입니다. 1·3·5·10·12번은 Daybreak 수정안을
기존 빌드 및 수집 조건에 맞게 보완했고, 나머지 7건은 수집기와 배포 도구에서 조치했습니다.

| 번호 | 항목 | 적용한 조치 |
|---|---|---|
| 1 | 배포 빌드의 Go 설정 | 상속된 Go 설정을 차단하고 모듈을 임시 작업 공간에서 검증합니다. 사용자 지정 Go는 검증된 절대 경로와 SHA-256을 요구합니다. 오프라인 캐시와 사내 미러를 지원합니다. |
| 2 | 이미지 아카이브의 출처 해시 | 압축 해제와 SHA-256 계산에 같은 입력 스트림을 사용합니다. |
| 3 | OCI 레이어 검증 비용 | 기존 256개 레이어 상한을 먼저 확인합니다. 검증한 동일 레이어의 해시를 재사용하고 레이어 순서를 보존합니다. |
| 4 | Python·Java ZIP 내부 목록 | ZIP 내부 목록을 인덱싱하기 전에 바이트 수와 항목 수를 제한합니다. ZIP64와 중첩 Java 수집을 지원하며, 중첩 검증에는 임시 디스크를 사용할 수 있습니다. |
| 5 | 저장 레이어의 삭제 표시 | 삭제 표시의 대상이 올바른지 확인합니다. 정상적인 파일 삭제와 opaque 디렉터리 처리를 지원합니다. |
| 6 | 컨테이너·이미지의 결과 경로 | 항목마다 출력 디렉터리를 배타적으로 확보합니다. 같은 이름이 충돌하면 고유한 접미사를 쓰고 실제 경로를 결과 목록에 남깁니다. |
| 7 | 오프라인 권고의 버전 대조 작업량 | 정확 버전 목록을 미리 인덱싱하고 작업량과 결과 크기를 제한합니다. 평가 중 취소를 확인합니다. |
| 8 | 최적화된 Python에서의 배포 QA | Python 최적화 모드에서 QA와 최종 포장을 중단합니다. QA 증적을 배포 대상 실행 파일의 SHA-256에 연결합니다. |
| 9 | 사전 탐색 이후 파일 읽기 범위 | 패키지·보조 수집기가 사전 탐색으로 확인한 루트와 범위 안에서 파일을 엽니다. 범위 내에서 해석된 심볼릭 링크를 지원하고 안전하게 읽을 수 없어진 항목은 결과에 기록합니다. |
| 10 | 짧은 containerd ID | 짧은 ID는 그대로 표시하고 긴 ID는 안전하게 줄입니다. |
| 11 | SBOM 버전 필드와 PURL 충돌 | RPM epoch 표기를 고려해 버전 정보를 대조합니다. 충돌하는 구성요소는 `review_required`로 기록합니다. |
| 12 | 호스트·저장 레이어의 디렉터리 탐색 | 항목을 256개씩 읽고 탐색 중 취소를 확인합니다. 일반 파일 수 한도와 심볼릭 링크·특수 항목 한도를 별도로 적용합니다. |

### 1.6·1.7 동시 출력과 라이선스

`--cyclonedx-17`을 지정한 경우에만 `sbom.cdx-1.7.json`을 추가합니다. 기본
`sbom.cdx.json`은 1.6이며 SPDX 파일은 2.3입니다. `--format both`에서는 세 파일,
`--format cyclonedx`에서는 두 CycloneDX 파일을 생성하고, `--format spdx`와 동시
출력 옵션의 조합은 출력 생성 전에 거부합니다. 같은 인벤토리를 사용하므로 추가
수집을 수행하지 않습니다.

Linux amd64의 동시 출력은 결과 7개, 기본 출력과 CycloneDX 전용 동시 출력은 각각
6개 체크섬을 통과했습니다. macOS ARM64 기본 자산의 동시 출력과 Linux ARM64
디렉터리 wrapper의 동시 출력도 각각 6개 체크섬을 통과했습니다. 파일 수는 수집
명령과 컨텍스트 포함 여부에 따라 달라지므로 고정 성공 조건으로 사용하지 않습니다.

공식 1.7.1 스키마 묶음을 커밋 `b29bae660048e0ad2fbc5f2972927b442ce951c4`와
SHA-256으로 고정하고 오프라인 검증했습니다. 1.6의 라이선스 ID 704개와 1.7의
811개를 각각 대조했으며, 추가된 107개 ID는 1.6에서 `license.name`, 1.7에서
`license.id`로 보존합니다. 버전별 스키마 통과와 구성요소·근거·라이선스 의미·관계·
수집 범위의 동등성을 함께 확인했습니다. 재현 절차는 [검증 안내](verification.ko.md)에
있습니다.

현재 개발 빌드는 실제 x86_64 물리 서버, Windows, BMC·OT 장비 또는 새 Ubuntu·Oracle
커널 VM 전체 회귀로 검증하지 않았습니다. 기존 버전의 실제 커널 VM 통과를 현재
빌드의 재실행 결과로 해석하지 않습니다.

## 0.1.4 디렉터리 전용 실행과 최종 배포 식별

0.1.4는 기존 `scan --target <디렉터리> --no-context`를 사용하는 `scan-directory.sh`와 실행 안내를 포함합니다. 특정 디렉터리와 하위만 수집하고 호스트 컨텍스트·라이브패치 조회는 실행하지 않습니다. 디렉터리 밖의 구성요소와 밖으로 향하는 심볼릭 링크가 표준 SBOM에 포함되지 않는지, 공백 경로·제한 해제·잘못된 옵션 거부를 별도로 검증합니다.

이번 최종 실행파일의 검증과 한계는 동봉 `VERIFICATION.json` 및 빌드 PC의 `dist/evidence/v0.1.4/final-verification.json`으로 확인합니다. 아래 기록은 과거 이력이며 새 빌드의 검증 근거를 대신하지 않습니다.

## 0.1.3 최종 배포 검증 식별

0.1.3은 `--max-files`와 수집 시간 제한 해제, helper의 수집 옵션 전달 및 제한 원인 기록을 추가하는 배포입니다. 파일 수 기본 상한은 1,000,000개이며 `--max-files 0`은 해제, 시간 기본 상한은 30분이며 `--timeout 0` 또는 `0s`는 해제입니다. Ctrl+C 취소와 기존 수집 경계는 유지합니다.

새 최종 바이너리의 실제 시험 결과는 동봉 `VERIFICATION.json` 및 `dist/evidence/v0.1.3/final-verification.json`의 SHA-256과 연결해 확인합니다. 이 문서의 과거 결과를 새 바이너리의 통과 증거로 사용하지 않습니다. 파일 수 상한 초과·무제한·취소 처리와 `collection.json`의 `limits`/`filesystemFileCount` 및 구조화된 제한 사유는 새 릴리스의 별도 검증 대상입니다.

## 과거 검증의 명시적 한계와 미검증

- 실제 x86_64 물리 서버에서는 아직 실행 검증하지 않았습니다. 위 VM은 공식 RHCK·UEK 커널과 Oracle Linux 8.2 사용자 공간의 custom initramfs 직접 부팅 시험입니다. 일반 OS 설치 프로그램·GRUB·UEFI/Secure Boot·systemd 전체 부팅·SELinux enforcing·운영 서비스 통합은 확인하지 않았습니다.
- macOS ARM64 Docker의 amd64 ptrace/strace는 레지스터를 잘못 해석하는 현상이 있어 해당 로그를 무통신 증거로 사용하지 않았습니다. 대체 QEMU guest syscall trace는 실제 amd64 실행 파일의 게스트 동작 증거이며 실제 x86_64 커널에서의 추적과 다릅니다.
- Tracker는 두 표준 SBOM 업로드를 검증했습니다. `context.json`·`collection.json`·`inventory.syft.json` 부가 자료의 자동 반입·화면 표시·백포트/CVE 적용 조건 자동 판정은 현재 지원 완료로 주장하지 않습니다.
- 라이브 파일시스템 수집은 스냅샷이 아닙니다. 수집 중 패키지 설치·업데이트·파일 교체가 있으면 시점이 다른 정보가 섞일 수 있으므로, 변경이 적은 시간에 수행하거나 읽기 전용 OS/파일시스템 스냅샷을 대상으로 사용하세요. 수집기가 정합성 있는 원자적 OS 스냅샷을 만든다고 보장하지 않습니다.
- 패키지 버전·설정 선언·모듈 미관측만으로 CVE 영향 여부나 안전성을 판정하지 않습니다. 상용 제품의 알려지지 않은 patch inventory 형식과 식별정보 없는 바이너리는 unknown/미검증 범위로 남습니다.
